This chapter explains the methodology used to build and evaluate a prototype system for static
\gls{malware} analysis supported by \glspl{llm} and \glspl{rag}. The system runs two pipelines on
the same set of samples. The first is a baseline classifier that combines \gls{virustotal} tags
with heuristics taken from \gls{ghidra}'s static analysis, such as imports, functions, and strings.
The second is an \gls{llm}-based pipeline that uses the same static features but also brings in
external context through a retrieval component from a \gls{rag} enabled datastore. Running both
pipelines in parallel makes it possible to compare accuracy, the relevance of supporting evidence,
and the clarity of explanations.

The choice to use \glspl{llm} in this way builds on recent work by Fujii and
Yamagishi~\cite{fujii2024llm}, who showed that models like \gls{gpt4o} can interpret decompiled
code and extracted metadata for classification tasks. Broader
surveys~\cite{nourmohammadzadeh2024llmsurvey,ferrag2024allinsights,metta2024generativeai} confirm
the growing role of \glspl{llm} in security analysis, particularly where interpretability and
contextual reasoning are important. The comparative setup also reflects the practitioner view
described by Wong et al.~\cite{wong2021practice}, where simple, transparent heuristics remain
central to \gls{malware} triage.

Using \glspl{rag} introduces new risks. As Zou et al.~\cite{zou2024poisonedrag} note, retrieval
pipelines can be poisoned or manipulated, leading to distorted outputs. To address this, the data
for the corpus comes from a selection of trusted sources, including VX-Underground APT reports,
MalwareBazaar submissions, and Malpedia documentation. The provenance of these sources reduces the
chance of corrupted context and strengthens the reliability of the retrieval process.

\section{Research Design}\label{sec:ResearchDesign}
% Describe the nature of your research: exploratory, experimental, comparative.
% Explain the reasoning for using a prototype-based implementation and evaluation.
% Emphasize that your approach avoids LLM fine-tuning and instead relies on
% prompt engineering and external context via RAG.
The research is experimental and exploratory, aimed at testing whether \glspl{llm} combined with
\glspl{rag} can strengthen static \gls{malware} analysis. Instead of training a new model or
fine-tuning existing ones, the study uses a \textbf{prototype-based dual-pipeline design} to
compare two independent approaches under the same conditions:
\begin{itemize}
      \item \textbf{Baseline Classifier:} A rule-based system that fuses
            \gls{vt} tags with heuristics extracted from \gls{ghidra}. Features such
            as imports, functions, and strings are processed into rules that emulate
            the quick, interpretable triage used in analyst
            workflows~\cite{wong2021practice}.
      \item \textbf{LLM + RAG Classifier:} A pipeline built on \gls{haystack},
            using \gls{postgresql} with \gls{pgvector} to retrieve relevant context
            documents. Extracted features and retrieved context are combined into
            structured prompts and passed to an \gls{llm} (e.g., \gls{gpt4o})
            for classification and explanation.
\end{itemize}

This design reflects earlier work by Fujii and Yamagishi~\cite{fujii2024llm}, who showed that
general-purpose \glspl{llm} can interpret decompiled code and static features to support
classification. It also builds on Wong et al.~\cite{wong2021practice}, who describe the role of
lightweight heuristics in everyday malware triage. The pipelines are evaluated strictly in
\textbf{inference mode}, following Gao et al.~\cite{gao2023retrieval}, who highlight how
\glspl{rag} can improve reasoning without retraining by injecting relevant external knowledge into
prompts.

Because retrieval systems can be manipulated, the risks of hallucination or poisoning identified by
Zou et al.~\cite{zou2024poisonedrag} are addressed by strict control over data provenance: only
curated, high-quality sources (VX-Underground, MalwareBazaar, and Malpedia) are ingested into the
datastore. All outputs are logged for traceability and later comparison.

\subsection{Experimental Workflow}\label{subsec:ExperimentalWorkflow}
Each sample is processed through both pipelines in parallel to produce outputs under identical
input conditions. Those outputs follow a specific pattern outlined on the next chapter. This setup
allows side-by-side benchmarking and highlights the contribution of \gls{llm}-based reasoning when
compared to static heuristics alone.

The workflow for each sample is as follows:
\begin{enumerate}
      \item \textbf{Static Feature Extraction:} Performed with \gls{ghidra} and
            processed into a structured form as can be seen in section ~\ref{subsec:StaticFeatureExtraction}.

      \item \textbf{Pipeline 1 -- Baseline Classifier:}
            \begin{itemize}
                  \item Extracted features are matched against heuristic rules (e.g., suspicious imports, entropy
                        thresholds).
                  \item On demand, \gls{vt} metadata are acquired (if available) and compared against the heuristic
                        evaluation through a decision engine to standardized family labels when available.
                  \item Output includes classification, triggered heuristics, and a confidence score.
            \end{itemize}

      \item \textbf{Pipeline 2 -- LLM + RAG Classifier:}
            \begin{itemize}
                  \item Extracted features are used to query the \gls{haystack}+\gls{postgresql}+\gls{pgvector} datastore.
                  \item Retrieved documents and features are embedded into a prompt template.
                  \item Prompt is passed to an \gls{llm} (e.g., \gls{gpt4o}) for inference.
                  \item Output includes classification, explanation, and reasoning trace.
            \end{itemize}

      \item \textbf{Logging and Storage:}
            \begin{itemize}
                  \item Both pipelines log their outputs, including:
                        \begin{itemize}
                              \item Sample hash (SHA256)
                              \item Pipeline name (Baseline or LLM+RAG)
                              \item Classification result
                              \item Confidence score
                              \item Explanation or triggered rules
                              \item Timestamp and runtime metadata
                        \end{itemize}
                  \item All results are indexed by sample hash and timestamp for reproducibility and evaluation.
            \end{itemize}
\end{enumerate}

The system ingests and analyzes \glspl{malware} samples through a modular pipeline that allows
reproducibility, parallel execution of different analysis methods, and detailed logging. As shown
in Figure~\ref{fig:system_architecture}, the architecture is built around two pipelines that run
side by side: a baseline classifier using static heuristics and \gls{vt} metadata, and an

same input sample and output a classification with supporting metadata.

\subsection{Malware Sample Ingestion}\label{subsec:MalwareSampleIngestion}
The system accepts samples in Windows executables (Portable Executable or \gls{pe}) format, such as
\texttt{.exe}, \texttt{.dll}, and \texttt{.sys} files. Each binary is indexed by its SHA256 hash
and stored locally for analysis.

\subsection{Static Feature Extraction with Ghidra}\label{subsec:StaticFeatureExtraction}
Static features are extracted through an automated \gls{ghidra} installation controlled with
\texttt{pyghidra}. This setup supports batch decompilation and scripted analysis. Extracted
features include:
\begin{itemize}
      \item \texttt{Program information}: Summary metadata about the binary with
            fields like original file name, file format, binary architecture, file
            size, etc.
      \item \texttt{Functions summary}: Summary of the functions discovered in the binary.
      \item \texttt{Full code of decompiled functions}: Decompiled function representations for higher-level review.
      \item \texttt{Imported Functions/API}: Imported API/function names from external libraries/DLLs.
      \item \texttt{Strings}: Printable strings extracted from the binary.
      \item \texttt{Memory Sections}: Memory/PE sections with names, sizes, attributes (e.g., entropy).
      \item \texttt{Exported}: Symbols/functions the binary exports (if any).
      \item \texttt{Entry Points}: Entry point addresses or function names identified.
\end{itemize}

These features are logged to a structured datastore and passed to both pipelines. Using
\gls{ghidra} ensures consistency across runs and provides visibility into sample internals.

\subsection{Pipeline A -- Baseline Classifier}\label{subsec:StaticTagBasedClassification}
The baseline pipeline reconciles two sources of evidence: static heuristics derived from
\gls{ghidra} and tag information from \gls{vt}. Extracted features are matched against heuristic
rules (e.g., entropy thresholds, suspicious imports), producing an internal score and confidence.
In parallel, \gls{vt} engine results are aggregated into a consensus score with a confidence value
based on coverage, recency, and naming consistency. A reconciliation layer then fuses these signals
using a weighted approach that adjusts for conflicts, applies penalties for weak evidence, and can
abstain when both sources disagree with high confidence. The output is a classification label,
score, and explanation trace. This design provides a transparent reference point for comparison and
reflects the reconciliation logic described in Section~\ref{subsec:BaselinePipeline}.

\subsection{Pipeline B -- LLM+RAG Classifier}\label{subsec:RAGBasedClassification}
The second pipeline integrates retrieval and model-based reasoning. Extracted features are
transformed into queries against a datastore (\gls{postgresql}+\gls{pgvector}) containing embedded
threat intelligence documents. Relevant documents are retrieved using \gls{haystack} and merged
with the static features into a structured prompt. The prompt is then passed to an \gls{llm} such
as \gls{gpt4o}, which produces a classification and supporting explanation. Details are given in
Section~\ref{subsec:LLMRAGPipeline}.

\subsection{Logging and Result Storage}\label{subsec:LoggingAndResult}
Both pipelines record their outputs using a consistent schema with:
\begin{itemize}
      \item Sample hash, timestamp, and pipeline identifier
      \item Classification label, score, and explanation
      \item Supporting metadata, latency, and reference sources
\end{itemize}
These logs provide the basis for reproducibility and comparative evaluation (Section~\ref{sec:EvaluationFramework}).

\section{Data Sources}\label{sec:DataSources}

The system relies on two categories of input: malware binaries for analysis, and external
intelligence documents for retrieval. As shown in Figure~\ref{fig:system_architecture}, both
pipelines begin with the same samples but diverge in how they use supporting data. The baseline
reconciles static heuristics with \gls{vt} tags, while the \gls{llm}+\gls{rag} pipeline augments
static features with retrieved context.

\subsection{Malware Samples Sourcing}\label{subsec:MalwareSamplesSourcing}
The main input focuses on \gls{pe} files of five common malware categories found in systematic
reviews~\cite{berrios2025malware,abrazak2016rise,mat2021systematic}: \textbf{Trojan},
\textbf{Ransomware}, \textbf{Botnet}, \textbf{Worm}, and \textbf{Rootkit}. Three representative
samples are drawn at random for each type (15 total) from \gls{vt} and/or \gls{malwarebazaar}, and
analyzed by both pipelines. To avoid biases, these samples's metadata were not ingested onto the
\gls{rag} datastore.

The \gls{pe} file format was chosen for this research as it is the standard for Windows executables
(e.g., \texttt{.exe}, \texttt{.dll}), is widely used in static \gls{malware} analysis due to its
rich structural features such as headers, import/export tables, and embedded
strings~\cite{fedak2020fundamentals}.

Each sample is catalogued with its SHA256 hash and timestamp. They are obtained from:
\begin{itemize}
      \item \textbf{\gls{malwarebazaar}}: An open repository maintained by
            abuse.ch, providing recent PE malware binaries for research.
      \item \textbf{\gls{vt}}: Accessed through its API, supplying binaries, scan metadata, and labeling tags.
\end{itemize}

\subsection{Baseline Metadata Sources}\label{subsec:BaselineSources}
The baseline analysis pipeline does not require external contextual data to work, however it uses a
set of parameters that, when combined with the built in rules, define the thresholds and tune the
sample analysis score and reconciliation strategy that fuses heuristics derived from \gls{ghidra}
with consensus scores from \gls{vt}. As can be seen at section ~\ref{subsec:BaselinePipeline}.

\subsection{RAG Corpus Data Sources and Construction}\label{subsec:RAGCorpusConstruction}
The \gls{llm}+\gls{rag} pipeline relies on a dedicated corpus of contextual documents to provide
grounding during inference. This corpus was assembled through the ingestion process described in
Section~\ref{subsec:RAGIngestionPipeline}, and populated with high-quality open sources covering
different levels of malware knowledge. Three main categories of data were included:

\begin{itemize}
      \item \textbf{VX-Underground APT Writeups}: All Advanced Persistent Threat (APT) reports
            published between 2022 and August 2025 were downloaded and ingested. These reports
            contain adversary tactics, binary structures, and reverse engineering notes. The data
            were collected following project guides~\footnote{\url{https://github.com/andremmfaria/rexis/blob/main/guides/DataSourcingVXUnderground.md},
                  \url{https://github.com/andremmfaria/rexis/blob/main/guides/IngestVXUnderground.md}}.

      \item \textbf{Malpedia Documentation}\cite{plohmann2017malpedia}: Family-level articles and
            technical descriptions were retrieved from Malpedia between 2022 and August 2025.
            These documents include IOCs, YARA rules, and summaries of static and behavioral
            traits. Some articles could not be included due to scraping failures, caused by
            protected pages, removed content, timeouts, or server errors (e.g., HTTP 503). Collection
            details are provided in the project guide~\footnote{\url{https://github.com/andremmfaria/rexis/blob/main/guides/DataSourcingMalpedia.md}}.

      \item \textbf{MalwareBazaar Metadata}: Metadata records were retrieved through the
            \gls{malwarebazaar} API using batch queries. Tags such as \textbf{Trojan},
            \textbf{Ransomware}, \textbf{Botnet}, \textbf{Worm}, \textbf{Rootkit}, and
            \textbf{exe} were selected to align with the focus of this study on \gls{pe}-based malware.
            The metadata include sample hashes, tags, and antivirus results. Only metadata were
            ingested; raw binaries were excluded to keep the datastore limited to contextual
            evidence.
\end{itemize}

\vspace{0.5em}
All documents were normalized, segmented, and embedded using the \gls{haystack} framework. Each
record was enriched with metadata fields such as source, document type, family or actor (if
available), and timestamp. The processed chunks were then stored in a \gls{postgresql}+\gls{pgvector}
datastore for semantic retrieval during inference (Figure~\ref{fig:rag_ingestion}).

\subsection{Labeling}\label{subsec:Labeling}
Samples are annotated using metadata from \gls{vt} when analysed through the baseline pipeline (see
section \ref{subsec:BaselinePipeline}). This provides a consistent benchmark for comparing the
baseline and \gls{llm}+\gls{rag} pipelines in terms of accuracy and explanation quality.

\subsection{Baseline Pipeline}\label{subsec:BaselinePipeline}
% Covers the non-LLM static pipeline:
% - Input format malware binaries.
% - Feature extraction via Ghidra (e.g., strings, imported functions).
% - Logging and preprocessing.
% - Hybrid classifier:
%   - **Heuristics**: Signature-based and rule-based logic.
%   - **VirusTotal**: Metadata correlation and mapping.
%   - **Decision engine**: Fuses the heuristic result with data from VT
% - Output classification format.
% - Technologies: PyGhidra, custom heuristics, VirusTotal API, Decision engine.
The baseline pipeline provides a deterministic static classification process that does not rely on
\glspl{llm}. It serves as a benchmark for comparison with the \gls{rag}-enhanced pipeline. The
approach combines custom heuristics with \gls{virustotal} metadata, using a reconciliation strategy
to produce a single canonical label for each sample.

\vspace{0.5em}
\noindent\textbf{Input Format:} The pipeline processes only \glspl{pe}, the native format for
Windows executables. These files were chosen for their structural consistency and widespread use in
malware distribution, which makes them well-suited for rule-based static
analysis~\cite{fedak2020fundamentals}.

\vspace{0.5em}
\noindent\textbf{Feature Extraction:} Static features are extracted from binaries using
\gls{ghidra} with its Python API \texttt{PyGhidra}. The automated extraction
step collects data based on \gls{ghidra}'s automated binary detection engine.

These features (outlined on section ~\ref{subsec:StaticFeatureExtraction}) are extracted,
serialized into JSON files for ease of extraction and usage.

\vspace{0.5em}
\noindent\textbf{Preprocessing and Logging:} Extracted features are normalized and deduplicated,
with all values logged for reproducibility. These logs form the structured input to the
classification stage.

\vspace{0.5em}
\noindent\textbf{Hybrid Classification Strategy:} Classification is performed by combining two
sources of evidence:
\begin{itemize}
      \item \textbf{Rule-Based Heuristics:} A lightweight decision engine evaluates static signals
            such as suspicious API calls (\texttt{CreateRemoteThread}, \texttt{VirtualAllocEx}),
            packed or encrypted sections, and known obfuscation markers. These rules produce
            heuristic labels such as ``ransomware-like'' or ``downloader''~\cite{gaber2024malware,
                  cassanova2022systematic}.
      \item \textbf{VirusTotal Tags:} For each sample, the \gls{virustotal} API is queried using the
            SHA-256 hash. Family names and vendor tags (e.g., \texttt{AgentTesla}, \texttt{Emotet})
            are retrieved and normalized into canonical categories, reducing variation between
            vendors~\cite{wong2021practice}.
\end{itemize}

\vspace{0.5em}
\noindent\textbf{Reconciliation Logic:} The final decision engine fuses heuristic output with
\gls{virustotal} metadata:
\begin{itemize}
      \item If both sources agree, the label is accepted directly.
      \item If they diverge, the \gls{virustotal} label takes precedence unless heuristic confidence surpasses
            a defined threshold.
      \item In ambiguous cases (e.g., low-confidence heuristics or missing \gls{virustotal} tags), the decision
            engine applies weighted rules to produce a best-effort classification.
\end{itemize}

This weighted reconciliation balances determinism with practical reliance on external consensus.
The full explanation on how the reconciliation engine works can be found on the project
repository\footnote{\url{https://github.com/andremmfaria/rexis/blob/main/guides/Reconciliation.md}}.

\vspace{0.5em}
\noindent\textbf{Output Format:} Each classification generates a structured report containing:
\begin{itemize}
      \item \textbf{Canonical Family Label:} The reconciled family name (e.g., \texttt{LokiBot}),
            chosen after harmonizing vendor tags and heuristic results.
      \item \textbf{Classification Source:} Indicates whether the final decision was based on
            heuristics, \gls{virustotal} tags, or a weighted combination of both.
      \item \textbf{Confidence Score:} A normalized value representing the strength of heuristic
            evidence, used when reconciling conflicting results.
      \item \textbf{Triggered Rules:} The specific heuristic rules that fired, providing transparency
            into why a heuristic label was assigned.
      \item \textbf{VirusTotal Matches:} The number of antivirus engines on \gls{virustotal} that
            agreed on the family or type, offering a measure of external consensus.
      \item \textbf{Metadata Snapshot:} Contextual information including file hash, timestamp, PE
            size, and section-level details, retained for audit and traceability.
\end{itemize}

The report structure is output in JSON format, enabling side-by-side comparison with the output of
the \gls{rag}-based pipeline.

\vspace{0.5em}
\noindent\textbf{Technologies Used:}
\begin{itemize}
      \item \textbf{Ghidra + PyGhidra} -- Automates feature extraction from binaries inside \gls{ghidra}.
      \item \textbf{Custom Heuristic Engine} -- Implements static rules for classification based on
            imports, entropy, and string analysis.
      \item \textbf{VirusTotal API} -- Provides external metadata, including family names and vendor
            detections, to enrich local heuristics.
      \item \textbf{Decision Engine} -- Fuses heuristic and \gls{virustotal} results, applying
            reconciliation rules to produce a single canonical label and confidence measure.
      \item \textbf{Logging Layer} -- Ensures extracted features, intermediate results, and
            final outputs are consistently structured and reproducible for evaluation.
\end{itemize}
The user has the option to not include \gls{virustotal} data on the pipeline. This makes the
decision engine pass through the result from the heuristics engine.

\noindent A detailed breakdown of the baseline pipeline design and decision logic is available

\subsection{LLM+RAG Pipeline}\label{subsec:LLMRAGPipeline}
% Details the enhanced pipeline:
% - Uses same features as baseline up to preprocessing.
% - **Semantic query** creation via Haystack.
% - **Contextual document retrieval** from pgvector vector store.
% - **Prompt construction** via template builder + compliance filter.
% - **Inference** using OpenAI's GPT-4 API.
% - Justification for not fine-tuning (focus on zero-shot generalization and reproducibility).
% - Output handling and logging.
The LLM+RAG pipeline integrates large language models with retrieval-augmented generation to extend
the scope of static malware classification. Unlike the baseline, this approach uses semantic
retrieval over a curated corpus of threat intelligence to provide context-aware inference and
explanations. The method emphasizes inference-time reasoning instead of pre-trained classification
logic, supporting zero-shot generalization without fine-tuning.

\vspace{0.5em}
\noindent\textbf{Input Format and Feature Extraction:} The pipeline begins in
the same way as the baseline one. Each \gls{pe} sample is processed with
\gls{ghidra} through \texttt{PyGhidra}, producing static features such as the
ones seen in section \ref{subsec:StaticFeatureExtraction}. These features are
logged into JSON format for use in later stages.

\vspace{0.5em}
\noindent\textbf{Semantic Query Generation:}
After feature extraction and preprocessing, the pipeline converts selected static attributes into a
semantic query. Extracted values such as API imports, section entropy, and embedded strings are
serialized into a structured textual representation. This representation is then embedded using
OpenAI’s \texttt{text-embedding-3-small} model, which produces dense vector representations
suitable for semantic search. By translating low-level static features into natural-language-like
descriptions, the system allows the retrieval engine to align binary characteristics with external
threat intelligence documents. For example, a sample that imports
\texttt{CreateRemoteThread}, \texttt{VirtualAllocEx}, and contains obfuscated networking strings
would yield a query embedding that captures both behavioral and structural intent. The generated
query vector is logged along with metadata such as chunk size, token count, and timestamp to ensure
traceability.

\vspace{0.5em}
\noindent\textbf{Contextual Document Retrieval:}
The embedded query is passed to a hybrid retriever implemented in \gls{haystack}. This retriever
combines dense vector similarity search (via \gls{pgvector}) with keyword-based BM25 retrieval,
ensuring that both semantically similar and lexically overlapping documents can be surfaced.
The underlying datastore is a PostgreSQL database enhanced with the \texttt{pgvector} extension,
which holds embeddings of curated malware corpora sourced from MalwareBazaar JSON records,
VX-Underground APT reports, and Malpedia articles (see~\ref{subsec:RAGIngestionPipeline}).
Documents are preprocessed into uniform chunks before embedding, with each chunk linked
to metadata such as source type, family/actor tags, original filename, and publication date.
This approach follows Gao et al.~\cite{gao2023retrieval}, who show that retrieval improves
reliability by grounding model outputs in external knowledge.

When a query is executed, the top-$k$ candidate documents are returned along with their cosine
similarity scores, source identifiers, and document IDs. If reranking is enabled (via a
cross-encoder model such as \texttt{gpt-4o-mini}), the candidate set can be refined to prioritize
documents with higher contextual relevance; by default, this step is skipped to reduce latency. All
retrieval events are logged, including query latency, document ranks, and similarity values. This
structured retrieval process ensures that every classification decision by the model can be traced
back to specific external evidence, maintaining transparency and reproducibility.

\vspace{0.5em}
\noindent\textbf{Prompt Construction:}
Once the top-$k$ documents are retrieved, they are combined with the extracted static features into
The structured prompt template consists of the following key components:
\begin{itemize}
      \item \textbf{Concise summary of static attributes:} Includes details such
            as API calls, entropy values, and extracted strings from the binary.
      \item \textbf{Retrieved contextual documents:} Presents the titles and
            relevant excerpts from the documents retrieved during semantic search.
      \item \textbf{Explicit instructions:} Directs the model to classify the
            sample, justify the decision with supporting evidence, and highlight
            related malware families if applicable.
\end{itemize}
Prompt construction is handled programmatically to ensure consistency across all samples. Sensitive
content such as raw hex dumps, shellcode, or very large decompiled blocks is filtered out to
mitigate prompt injection risks and to remain within token limits. Each generated prompt is logged
with metadata including query ID, sample hash, document IDs, and token length, ensuring reproducible
execution. For more information see section \ref{subsec:PromptEngineering}.

\vspace{0.5em}
\noindent\textbf{LLM Inference and Response Handling:}
The completed prompt is submitted to \gls{gpt4o} via the OpenAI API to be used
strictly in inference mode. Removing the need for fine-tuning, and emphasizing
generalization from external context rather than learned weights. The LLM
produces a structured response containing a proposed malware family label,
justification using the retrieved evidence, and optional comparisons to related malware or tactics.

Response handling includes parsing the model output into structured fields (family label,
rationale, references). Additional metadata such as model identifier, temperature setting, latency,
and token usage are recorded. These details provide transparency in model performance and
facilitate later analysis of cost, efficiency, and reproducibility.

\vspace{0.5em}
\noindent\textbf{Output Format:}
The output of the LLM+RAG pipeline is standardized to align with the baseline pipeline format while
capturing additional context. Each classification record includes:
\begin{itemize}
      \item \textbf{Sample identifiers:} SHA256 hash and timestamp of analysis
      \item \textbf{Predicted family label:} Canonicalized malware family or “unknown” if undecided
      \item \textbf{Supporting rationale:} Textual explanation generated by the LLM
      \item \textbf{Retrieved evidence:} List of document IDs, titles, source type (e.g., Malpedia, VX-U),
            and similarity scores
      \item \textbf{Model metadata:} Model name, API endpoint, token usage, and temperature setting
      \item \textbf{Performance metrics:} Latency measurements for embedding, retrieval, and inference
\end{itemize}

This uniform structure ensures comparability between the baseline and LLM+RAG pipelines while
providing additional layers of interpretability and traceability. By explicitly linking each
classification to both static features and external documents, the pipeline produces outputs that
are explainable, reproducible, and auditable.

\begin{itemize}
      \item \textbf{Ghidra + PyGhidra} -- Static feature extraction from binaries
      \item \textbf{Haystack} -- Query building and retrieval orchestration
      \item \textbf{PostgreSQL + pgvector} -- Vector store for the threat corpus
      \item \textbf{OpenAI API} -- Inference endpoints for \glspl{llm}
\end{itemize}

\subsection{RAG Ingestion Pipeline}\label{subsec:RAGIngestionPipeline}
% Describes how the vector database is constructed:
% - Input data sources (VX-Underground, Malpedia, MalwareBazaar).
% - Cleaning and normalization.
% - Chunking strategy.
% - Embedding model (e.g., OpenAI's `text-embedding-3-small`).
% - Insertion into PostgreSQL + pgvector via Haystack.

To support contextual retrieval in the \gls{rag}-enabled classification pipeline, a dedicated
ingestion workflow was implemented to populate the vector datastore with structured, semantically
rich documents. This pipeline is responsible for fetching, cleaning, chunking, embedding, and
storing threat intelligence content, ensuring that \glspl{llm} are grounded in verified sources
rather than generating unsupported inferences.

\vspace{0.5em}
\noindent\textbf{Input Data Sources:} Three primary sources form the corpus:
\begin{itemize}
      \item \textbf{VX-Underground APT Writeups} --~APT campaign documentation containing
            attacker TTPs, reverse-engineering notes, and contextual indicators. Collected
            via curated archive scraping and exposed through a Python interface.
      \item \textbf{Malpedia Documentation} --~Behavioral descriptions and malware family
            summaries, retrieved through \gls{malpedia}’s API endpoints (e.g., references,
            bibliographies). These provide canonical mappings of families and actors.
      \item \textbf{MalwareBazaar Metadata} --~Sample metadata, hashes, and tagging, retrieved
            via API and aligned with executable (e.g.\ \texttt{exe}) samples to match the scope of
            this project’s \gls{pe}-focused analysis.
\end{itemize}
Data from all sources is collected in their original formats (\gls{malpedia}'s
JSON, VX-Undergrounds's PDFs, Malpedia's HTML or text, etc.), as described on~\ref{subsec:RAGCorpusConstruction}.

\vspace{0.5em}
\noindent\textbf{Preprocessing and Cleaning:} The ingestion pipeline applies
normalization and filtering steps to maintain consistency across heterogeneous
sources:
\begin{itemize}
      \item Re-encoding to UTF-8 and removal of malformed characters
      \item Deduplication of repeated documents across feeds
      \item Removal of empty or trivial content blocks
      \item Uniform metadata enrichment, including document source, timestamp, malware family (if available),
            and threat category
\end{itemize}
This stage ensures downstream embeddings are consistent and traceable.

\vspace{0.5em}
\noindent\textbf{Chunking Strategy:} Documents are split into smaller units to fit within embedding
model limits\footnote{\url{https://platform.openai.com/docs/guides/embeddings\#embedding-models}}
and to maximize retrieval granularity. The strategy is tuned per document type:

\begin{itemize}
      \item \textbf{Prose (reports, articles)} --~Maximum 500 words per chunk with
            50-word overlap, sentence-boundary aware
      \item \textbf{Structured JSON/metadata} --~Maximum 4000 characters with
            400-character overlap, split by character range rather than sentence
      \item \textbf{Token-boundary fallback} --~If a chunk exceeds the model’s token
            limit (default 8192), it is split into smaller token batches without overlap
\end{itemize}
This strategy was required for the ingestion of documents of varying lengths and formats. The chunk
sizes per format were chosen based on statistical evaluation based on document density and information
richness~\footnote{\url{https://learn.microsoft.com/en-us/azure/search/vector-search-how-to-chunk-documents}}.

\vspace{0.5em}
\noindent\textbf{Embedding and Vectorization:} Prepared chunks are embedded
using OpenAI’s \texttt{text-embedding-3-small} model. Each chunk is converted
into a high-dimensional vector and paired with its metadata (source, family,
timestamp, embedding version). Embedding metadata is retained to allow model
versioning and reproducibility across experiments.

\vspace{0.5em}
\noindent\textbf{Database Insertion:} Chunks and embeddings are stored in
\gls{postgresql} with the \texttt{pgvector} extension, enabling efficient cosine
similarity search. Integration with Haystack handles bulk insertion, index
construction, and metadata filtering. Each row in the datastore contains:
\begin{itemize}
      \item Vector embedding
      \item Original text chunk
      \item Source metadata (filename, family/actor, source URL)
      \item Embedding version and timestamp
      \item Chunk indexing (position and total chunks for rejoining if needed)
\end{itemize}
This structure allows both fine-grained retrieval and reconstruction of the original document if required.

\vspace{0.5em}
\noindent\textbf{Technologies Used:} The ingestion pipeline is implemented in
Python and orchestrated using the following components:
\begin{itemize}
      \item \textbf{Haystack} --~For document chunking, embedding, and datastore integration
      \item \textbf{OpenAI API} --~For embedding generation
      \item \textbf{Custom Python Scripts} --~For source collection, reconciliation,
            and preprocessing
      \item \textbf{PostgreSQL + pgvector} --~For embedding storage and similarity search
\end{itemize}

\noindent Full technical details on the ingestion workflow used to build the RAG corpus and
scripts are provided in the guide:~\footnote{\url{https://github.com/andremmfaria/rexis/blob/main/guides/IngestionPipeline.md}}

\section{Prompt Engineering}\label{sec:PromptEngineering}
% Discuss how you craft prompts for different tasks: classification, explanation, and comparison.
% Include examples of how static features and retrieved context are structured in the prompt.
% Explain the decision to use GPT-4 in inference-only mode.
The design of prompts is central to the performance of the \gls{llm}+\gls{rag} pipeline. In this
study, prompts are assembled with a hybrid approach: a fixed system message that enforces output
schema and consistency, and a user message that presents static features and retrieved evidence in
a structured natural-language format. This balance preserves reproducibility while giving the model
a more interpretable context in which to reason.

\subsection{Prompt Structure}\label{subsec:PromptStructure}
Prompts follow a modular template with two main components:

\begin{itemize}
      \item \textbf{System Message:} Provides the role instruction and enforces the strict JSON schema
            required for output. The schema includes mandatory fields such as family label, classification,
            capabilities, tactics, supporting evidence, and an uncertainty measure. By fixing this schema at
            the system level, consistency is maintained across all samples.

      \item \textbf{User Message:} Assembled dynamically for each sample and divided into three parts:
            \begin{enumerate}
                  \item \textbf{Context Block:} A concise list of static features extracted from the binary,
                        such as API imports, section entropy values, and embedded strings, formatted as natural-language
                        bullet points.
                  \item \textbf{Retrieved Documents:} Up to three semantically similar documents retrieved from
                        the vector store. Each entry includes its source (e.g., Malpedia, VX-Underground), title or tag,
                        document ID, and a short snippet.
                  \item \textbf{Task Instructions:} A fixed directive asking the model to classify the sample into
                        a known family and either justify the decision with both static and retrieved evidence, or compare it with
                        related malware if applicable. This is controlled by the prompt variant (see section ~\ref{subsec:TaskTypes}).
            \end{enumerate}
\end{itemize}

\subsection{Filtering and Safety}\label{subsec:PromptFiltering}
Before submission, prompts are filtered to remove unsafe and/or irrelevant content and to apply
size filtering for the context window. Large hex dumps, decompiled blocks, or sensitive network
indicators are excluded to reduce noise and mitigate prompt-injection risks.

\subsection{Task Templates}\label{subsec:TaskTypes}
Three prompt variants are implemented to cover different reasoning demands:
\begin{enumerate}
      \item \textbf{Classification-Only:} Requests a family label based on static features and retrieved context.
      \item \textbf{Classification + Justification:} Requires the model to cite both static features and
            retrieved evidence when assigning a label.
      \item \textbf{Classification + Comparison:} Adds a comparative element, asking the model to relate
            the sample to known malware families or behaviors.
\end{enumerate}

These templates allow for observation of how the model responds to increasing cognitive
requirements while keeping the schema stable.

\subsection{Reproducibility and Versioning}\label{subsec:PromptVersioning}
Every prompt is versioned with a hash computed from the static features and retrieved document IDs.
This guarantees that a given model output can be traced back and reproduced even if the underlying
datastore or APIs are updated. Prompt versions and inference logs are stored alongside
classification results, forming the basis for later evaluation
(Section~\ref{sec:EvaluationFramework}).

\subsection{Prompt Example}\label{subsec:PromptExample}
The following excerpt illustrates how prompts are assembled in the \gls{llm}+\gls{rag} pipeline.
The system message enforces schema compliance, while the user message provides structured context,
retrieved documents, and a task directive. Only the user message is shown here for clarity.

\begin{quote}
      \texttt{Context:}
      - The file imports \texttt{CreateRemoteThread}, \texttt{VirtualAllocEx}, and \texttt{WriteProcessMemory}.
      - High entropy detected in \texttt{.text} and \texttt{.rsrc} sections.
      - Embedded strings include URLs (\texttt{hxxp://malicious-site.com}) and encoded PowerShell commands.

      \texttt{Retrieved Document [Malpedia: AgentTesla, DocID=malp-1234]}:
      \emph{``AgentTesla often uses process injection via RemoteThread APIs and
            obfuscates its communication channels with encoded PowerShell payloads.''}

      \texttt{Retrieved Document [VX-Underground: APT37, DocID=vx-5678]}:
      \emph{``APT37 campaigns leveraged DLL injection combined with custom packers,
            embedding URLs for remote payload retrieval.''}

      \texttt{Task:}
      Based on the static features and retrieved documents, classify the sample into
      a known family. Provide a JSON output following the schema, including:
      \begin{itemize}
            \item family label
            \item classification tags (e.g., trojan, stealer)
            \item capabilities and tactics
            \item 4--8 evidence items citing features and retrieved documents
            \item an uncertainty measure (low, medium, high)
      \end{itemize}
      If uncertain, return \texttt{"label": "unknown"} and \texttt{"uncertainty": "high"}.
\end{quote}

\section{Guardrails}\label{sec:Guardrails}
% Describes the safety and reliability mechanisms built into the LLM+RAG pipeline.
% Covers technical and procedural guardrails designed to prevent misuse, ensure ethical operation,
% and maintain the integrity of results. Topics include:
%   - Automated content filtering to block unsafe, sensitive, or harmful prompts and outputs.
%   - Rate limiting and API usage controls to prevent abuse and ensure compliance with service policies.
%   - Human-in-the-loop review for critical or ambiguous cases, especially where ethical or legal concerns arise.
%   - Logging and traceability of all inference and retrieval events for audit and reproducibility.

To mitigate the risks of inaccurate or wrongful classification in our LLM-RAG pipeline, we propose
a set of \emph{guardrail strategies} aimed at improving reliability, factual grounding, and
resistance to contextual bias. Each strategy is motivated by recent academic research on
hallucination mitigation, structured prompting, RAG behavior, and system-level guardrails.

\subsection{Rationale and Basis}
Retrieval‐Augmented Generation (RAG) improves factual grounding by retrieving and incorporating
external documents—but hallucinations can still arise from retrieval noise, lexical anchors, or
overreliance on cues such as family names~\cite{zhang2025hallucination}. Structured prompting and
multi-stage reasoning (e.g., hypothesize then verify) have been shown to reduce hallucination and
improve reliability~\cite{bechard2024reducing, lee2025finetune}. In parallel, system-level
\emph{guardrails} that sanitize inputs and enforce verification demonstrate stronger
trustworthiness in LLM deployments~\cite{han2025guardrail, magesh2025assessing}.

\subsection{Guardrail Components}
\begin{enumerate}
      \item \textbf{Name Redaction in Retrieved Passages.}
            Masking known family names or actor terms in retrieved context helps avoid anchoring
            bias. This approach aligns with input sanitization techniques advocated in safety‐critical
            LLM systems~\cite{han2025guardrail}.

      \item \textbf{Re-Rank by Technical Evidence, Not Lexical Signals.}
            Reordering retrieved passages based on domain-specific technical cues (e.g., API names,
            section labels) and down-weighting family name hits improves the factual relevance of
            input context~\cite{zhang2025hallucination, magesh2025assessing}.

      \item \textbf{Two-Stage Classification: Blind Hypothesis → Evidence Verification.}
            First generate a classification hypothesis based solely on structured features; then
            validate it using RAG context, encouraging verifiable reasoning. This mirrors structured
            output generation via RAG and helps reduce hallucination~\cite{bechard2024reducing, lee2025finetune}.

      \item \textbf{Post-Validation and Abstention on Insufficient Evidence.}
            If fewer than two RAG‐based evidence snippets support the claim, or if the proposed
            family aligns with masked tokens, the system abstains (labels “unknown\_family”). This
            enforces accountability and mitigates over-confident speculation~\cite{han2025guardrail, magesh2025assessing}.

      \item \textbf{Audit-Trail Metadata.}
            Every classification logs redacted names, re-ranked passages, blind vs. final
            hypotheses, evidence item count, and abstention status. Such transparency supports
            reproducibility and post-hoc analysis—a best practice in trusted AI systems~\cite{han2025guardrail}.
\end{enumerate}

\subsection{Workflow Summary}

\begin{center}
      \begin{tabular}{ll}
            \toprule
            \textbf{Step}                    & \textbf{Description}                                  \\
            \midrule
            1. Redaction                     & Remove family/actor names from retrieved texts        \\
            2. Re-Ranking                    & Score passages by technical relevance, penalize names \\
            3a. Blind Classification         & Hypothesize using structured features only            \\
            3b. Justification Classification & Validate hypothesis using sanitized RAG               \\
            4. Post-Validation               & Require $\geq$ 2 supporting quotes; abstain otherwise \\
            5. Audit Trail                   & Record metadata for analysis and trustworthiness      \\
            \bottomrule
      \end{tabular}
\end{center}

\subsection{Theoretical Justification}

\begin{itemize}
      \item \emph{RAG grounding} helps but isn’t sufficient for fidelity; targeted mitigation
            improves reliability in classification tasks \cite{zhang2025hallucination, bechard2024reducing}.
      \item \emph{Structured verification (hypothesis + evidence)} encourages factual reasoning
            and reduces spuriously confident labels \cite{bechard2024reducing, lee2025finetune}.
      \item \emph{System-level guardrails}, such as sanitization and abstention, are critical in0
            maintaining trust in deployed LLM systems \cite{han2025guardrail, magesh2025assessing}.
\end{itemize}

\section{Ethical Considerations}\label{sec:EthicalConsiderations}
% Ensure ethical use of malware datasets.
% Describe safety protocols: no execution of live malware, all samples are statically analyzed.
% Highlight responsible use of LLMs and privacy-conscious data handling if using
% VirusTotal.
The research presented in this study involves the use of malware samples, static code artifacts,
and third-party threat intelligence sources. Several precautions are taken to ensure that the study
adheres to ethical standards in cybersecurity research.

\subsection{Safe Handling of Malware Samples}
All malware samples are statically analyzed without execution. No sandboxing or dynamic behavior
monitoring is performed. Samples are stored in a secure, containerized, non-networked, isolated
environment with no file execution permissions. The analysis pipeline operates solely on extracted
features (e.g., strings, imports, entropy) and decompiled code sections.

Samples are sourced from public research repositories such as \gls{malwarebazaar} and
\gls{virustotal}, which provide malware binaries and metadata specifically for research and
detection engineering purposes. No private or unknown-origin malware is introduced into the
dataset.

\subsection{Use of Public and Licensed APIs}
All external APIs (OpenAI, VirusTotal, MalwareBazaar) are accessed through official channels with
proper authentication and rate limits. API usage complies with the respective Terms of Service, and
no bulk data scraping or unauthorized reverse engineering is conducted.

VirusTotal’s API is used strictly for metadata enrichment and tagging. No personal data,
user-uploaded files, or proprietary content is accessed or stored.

\subsection{Privacy and Data Anonymity}
No personal, user-identifiable, or system-specific data is involved in the research. All data used
is either public (e.g., APT reports) or anonymized (e.g., sample hashes). Retrieved documents are
cleaned to remove IP addresses, hostnames, or other sensitive references prior to embedding.

\subsection{Responsible Use of LLMs}
The use of \glspl{llm} in this study is limited to inference-only interactions. No fine-tuning is
performed. The prompts are explicitly filtered to exclude shellcode, network addresses, or exploit
payloads. The system is designed for classification and explanation, not for generating or
manipulating malware.

To prevent propagation of misleading or unsafe content, all generated responses are stored and
reviewed offline. In alignment with recommendations from recent LLM safety
surveys~\cite{ferrag2024allinsights, metta2024generativeai}, the system avoids code synthesis and
adheres to a read-only analysis posture.
