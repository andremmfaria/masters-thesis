This chapter presents the implementation details and key findings of the research system designed
to enhance static malware analysis using \glspl{llm} and \gls{rag}. It outlines the architectural
realisation of the proposed pipelines, describes how individual components were integrated, and
evaluates their performance across a representative corpus of malicious \glspl{pe} samples. The
experiments were conducted on a dataset of 20 malware samples across four commonly studied
families~\cite{berrios2025malware,abrazak2016rise,mat2021systematic} (see
Section~\ref{subsec:MalwareSamplesSourcing}), enabling comparative evaluation of classification
behaviour.

\section{Environment}\label{sec:Environment}

The experimental environment was built using a combination of open-source tools, APIs, and
containerised services, with an emphasis on modularity, reproducibility, and transparent workflows.
All experiments were executed on Ubuntu 24.04
LTS.\footnote{\url{https://releases.ubuntu.com/24.04/}} All development was carried out in
\gls{python}, with dependencies managed via isolated environments to ensure deterministic builds. A
step-by-step guide to the setup and configuration can be found in the project
repository~\cite{rexisRepo}.

The main tools and frameworks are:

\begin{itemize}
      \item \textbf{\gls{python}} --~Primary implementation language for orchestration logic and
            pipeline components. Python was chosen for its mature ecosystem in cybersecurity, data analysis,
            and \gls{machine-learning}.\footnote{\url{https://www.python.org}}

      \item \textbf{PDM (Python Development Master)} --~Manages dependencies and virtual
            environments. PDM provides deterministic builds and isolated execution, supporting reproducibility
            across runs and machines.\footnote{\url{https://pdm-project.org}}

      \item \textbf{\gls{postgresql} + \gls{pgvector}} --~Relational database\footnote{\url{https://www.postgresql.org}}
            extended with the \texttt{pgvector} module\footnote{\url{https://github.com/pgvector/pgvector}} for
            similarity search on embeddings. It serves as the vector store backing the retrieval stage of the
            \gls{rag} pipeline. The database is deployed in a Docker container for consistency and portability.

      \item \textbf{\gls{haystack}} --~Framework used to implement the \gls{rag} workflow, including
            ingestion, chunking, embedding, and retrieval. Its modular components simplify orchestration and
            integration with external \glspl{llm}.\footnote{\url{https://haystack.deepset.ai}}

      \item \textbf{\gls{gpt4o} (inference-only)} --~Used strictly in inference-only mode. No fine-tuning
            was performed, ensuring reproducibility across runs. The model is responsible for contextual
            reasoning and static feature analysis, driven by structured prompts enriched with retrieved
            evidence.\footnote{\url{https://platform.openai.com/docs/api-reference/introduction}}

      \item \textbf{\gls{ghidra} + PyGhidra} --~\gls{ghidra} is used as the static analysis and
            decompilation framework. PyGhidra provides bindings to automate extraction of imports,
            functions, strings, sections, entropy values, and decompiled code from \gls{pe} binaries,
            enabling feature logging at scale.\footnote{\url{https://github.com/NationalSecurityAgency/ghidra}}\footnote{\url{https://github.com/NationalSecurityAgency/ghidra/blob/master/Ghidra/Features/PyGhidra/src/main/py}}

      \item \textbf{Docker} --~Used to containerise core services such as \gls{postgresql} with
            \gls{pgvector}. Containerisation ensures reproducibility, isolation, and consistency
            across systems.\footnote{\url{https://www.docker.com}}

      \item \textbf{\gls{malwarebazaar} API + helper script} --~Samples for the evaluation cohort were
            downloaded using a helper script~\cite{rexisSamplesExtractorScript} that calls the
            MalwareBazaar API~\footnote{API docs: \url{https://bazaar.abuse.ch/api/}}.

      \item \textbf{\gls{virustotal} API} --~Supplies scan metadata, antivirus tags, and consensus labels
            across vendors. These labels support the baseline classifier and reconciliation logic, providing
            a benchmark for evaluation~\cite{rexisReconciliationGuide}.\footnote{\url{https://developers.virustotal.com/reference}}

      \item \textbf{\gls{vx-underground} and \gls{malpedia}} --~Additional data sources used to populate
            the retrieval corpus with threat intelligence reports, APT write-ups, and malware family and category descriptions.
            These documents strengthen contextual grounding in the \gls{rag} pipeline by supplying semantically
            rich background evidence.\footnote{\url{https://VX-Underground.org}}\footnote{\url{https://malpedia.caad.fkie.fraunhofer.de}}
\end{itemize}

\noindent
Version control was managed through Git and GitHub, ensuring traceability of code, configurations,
and experiment scripts. Each pipeline execution was logged with structured metadata, including sample
identifiers, timestamps, tool versions, prompt hashes, and retrieved document IDs, supporting full
auditability and reproducibility. Containerisation and PDM further guaranteed that results can be
replicated on any compliant environment with minimal configuration drift.

The system is implemented as a modular Python application structured around the
\texttt{Typer}\footnote{\url{https://typer.tiangolo.com/}} CLI framework. The codebase
(\texttt{src/rexis}) is organised to support three main operations: data ingestion, baseline static
classification, and enhanced \gls{llm}+\gls{rag} classification. Common modules handle
configuration, logging, and feature extraction, while each pipeline defines its own classification
logic. Documentation and usage examples for each pipeline are provided in dedicated guides
ingestion~\cite{rexisIngestionPipeline}, baseline~\cite{rexisBaselinePipeline}, and
LLM+RAG~\cite{rexisLLMRagPipeline}. The project can be found on the GitHub
repository~\cite{rexisRepo}.

\subsection{Common Modules}\label{subsec:CommonModules}
The following components are shared across all pipelines:

\begin{itemize}
      \item \textbf{Sample Loader:} Reads \gls{pe} binaries, computes hashes (SHA256, MD5),
            and registers samples in a consistent directory layout for reproducibility.

      \item \textbf{Ghidra Integration:} Static feature extraction is automated via
            \gls{ghidra} using the \texttt{PyGhidra} API. Features include imports, functions,
            printable strings, section entropy, entry points, and decompiled code.

      \item \textbf{Feature Extractor:} Serialises features into JSON and \texttt{pandas}
            DataFrames for consistency and downstream reuse.

      \item \textbf{Logger:} Structured logging captures runtime events, timestamps,
            tool versions, hashes, and prompt identifiers. This provides an audit trail
            for every classification decision.

      \item \textbf{Configuration Manager:} Runtime parameters such as API keys,
            thresholds, and feature toggles are handled by
            \texttt{dynaconf}\footnote{\url{https://www.dynaconf.com/}}, ensuring secrets
            are separated from code and allowing profile-specific overrides.

      \item \textbf{CLI Interface:} A unified \texttt{rexis} command provides access
            to all pipelines. Subcommands support ingestion
            (\texttt{rexis ingest}), baseline classification (\texttt{rexis run baseline}),
            and RAG-enhanced classification (\texttt{rexis run rag}).
\end{itemize}

\subsection{Data Ingestion Pipeline}\label{subsec:DataIngestionImpl}
The ingestion pipeline prepares the retrieval corpus by transforming raw threat intelligence into
searchable vector embeddings:

\begin{itemize}
      \item \textbf{Document Loader:} Collects documents from \gls{malwarebazaar},
            \gls{malpedia}, and VX-Underground, normalising metadata and assigning unique IDs.

      \item \textbf{Preprocessing Engine:} Cleans input by removing boilerplate,
            scripts, and noise, standardising text for downstream processing.

      \item \textbf{Chunker:} Splits long documents into sections sized for
            embedding-model token limits using heading- and length-aware heuristics.

      \item \textbf{Embedder:} Encodes chunks using OpenAI’s
            \texttt{text-embedding-3-small} model. Embeddings are processed in batches
            for scalability.

      \item \textbf{Vector Store Writer:} Stores embeddings and metadata in a
            \gls{postgresql}+\gls{pgvector} database. Haystack’s \texttt{DocumentStore}
            abstraction is used for indexing and similarity search.
\end{itemize}

Ingestion is automated via \texttt{rexis ingest --source=<name>} and supports incremental updates.
Prompt versioning ensures that classification results can always be traced to the exact retrieval
corpus state.

\subsection{Baseline Pipeline Implementation}\label{subsec:BaselineImplementation}
The baseline pipeline combines heuristic rules with VirusTotal metadata to provide a deterministic
classification strategy:

\begin{itemize}
      \item \textbf{Heuristic Classifier:} Applies manually curated rules to extracted
            features. For example, suspicious imports or anomalous entropy can trigger alerts.

      \item \textbf{VirusTotal Enricher:} Queries the \gls{virustotal} API for
            detections, tags, and metadata. Results are normalised to canonical category labels
            via a tag-mapping layer.

      \item \textbf{Decision Engine:} Reconciles heuristic outputs with VirusTotal
            consensus using confidence-weighted thresholds~\cite{rexisReconciliationGuide}.

      \item \textbf{Output Formatter:} Produces structured JSON summaries containing
            rules triggered, VirusTotal consensus, and final classification label.
\end{itemize}

\subsection{LLM+RAG Pipeline Implementation}\label{subsec:RAGImplementation}
The enhanced pipeline retrieves semantically relevant evidence and integrates it into structured
prompts for inference via GPT-4o:

\begin{itemize}
      \item \textbf{Semantic Query Builder:} Transforms extracted features into
            natural language queries, incorporating imports, strings, and header attributes.

      \item \textbf{Retriever:} Executes top-$k$ retrieval from the \gls{pgvector}
            store using Haystack, returning documents with IDs, scores, and snippets.

      \item \textbf{Prompt Builder:} Assembles prompts from static features,
            retrieved passages, and task instructions. Prompt schemas are fixed
            to ensure consistent outputs (see Section~\ref{sec:PromptEngineering}).

      \item \textbf{Guardrails Filter:} Sanitises prompts by removing hex dumps,
            sensitive domains, or oversized content, reducing injection risks
            (see Section~\ref{sec:Guardrails}).

      \item \textbf{Inference Client:} Submits prompts to GPT-4o via the OpenAI API,
            logging model ID, latency, and token counts for reproducibility.

      \item \textbf{Result Parser:} Extracts structured fields (family, classification tags,
            rationale, citations, uncertainty) from model outputs, aligning them with the
            evaluation framework (Section~\ref{sec:EvaluationFramework}).
\end{itemize}

This section details the design and execution of the evaluation. It defines the cohort and scope,
documents the exact commands used to run both pipelines, describes normalisation and metrics,
reports the results, and summarises data ingestion for the RAG corpus that supports retrieval in
the LLM+RAG pipeline (cf.\ Section~\ref{sec:DataSources}).

\subsection{Cohort and Scope}\label{subsec:CohortScope}
\textbf{20} Windows \gls{pe} samples were evaluated across four tags: \textbf{trojan}, \textbf{ransomware},
\textbf{botnet}, and \textbf{rootkit} (five per tag). The cohort was frozen on 24 Aug 2025;
duplicates were removed by SHA-256 and invalid PE files were excluded. Acquisition rules: (i) must
include the current tag, (ii) must include \texttt{exe}, (iii) must \emph{not} include any other
tag from the experiment’s tag set (except the current tag). Runs are driven directly via the CLI as
documented in the project guides. Samples were downloaded using a helper script that calls the
MalwareBazaar API~\cite{rexisSamplesExtractorScript};
archives were decompressed in bulk via a companion script~\cite{rexisDecompressSamplesScript}.
\texttt{truth\_category} reflects the MalwareBazaar acquisition tag recorded at selection time
(see Section~\ref{sec:Limitations} for ground-truth caveats).

\subsection{Analysis Execution Procedure}\label{subsec:ExecutionProcedure}
Both pipelines were executed under identical conditions (same sample order). CLI entry points and
options follow the repository guides~\cite{rexisBaselinePipeline,rexisLLMRagPipeline}.

All runs write a report (\texttt{ingest-analysis-\textless RUN\_NAME\textgreater{}}) with
timestamps, parameters, and environment. Documents are chunked, embedded (OpenAI embeddings), and
stored in \texttt{PostgreSQL}+\texttt{pgvector}, enabling hybrid retrieval in the LLM+RAG pipeline.

\subsection{Normalisation and Alignment}\label{subsec:NormalizationAlignment}
Outputs from both pipelines (baseline with and without \gls{vt} enrichment and LLM+RAG) were
aligned into a single comparison table. This enables one-to-one comparisons across all samples.

\vspace{0.5em}
The comparison outputs are organised on a table and its columns are:
\begin{itemize}
      \item \texttt{sha256}: Sample's SHA-256 hash (unique identifier).
      \item \texttt{truth\_category}: Ground-truth tag for the sample (trojan, ransomware, botnet,
            rootkit), defined by cohort selection via a helper script using the \gls{malwarebazaar}
            API~\cite{rexisSamplesExtractorScript}; the associated acquisition tag was recorded at selection time (cf. Section~\ref{sec:Limitations}).
      \item \texttt{vt\_malicious}: Number of VirusTotal engines that flagged the sample as malicious.
      \item \texttt{vt\_total}: Total number of VirusTotal engines that scanned the sample.
      \item \texttt{baseline\_label}: Raw label produced by the baseline (heuristics-only) pipeline.
      \item \texttt{baseline\_pred\_categories}: Inferred Baseline labels.
      \item \texttt{baseline\_duration\_sec}: Wall-clock runtime (seconds) for the baseline pipeline.
      \item \texttt{baseline\_vt\_label}: Raw label from the baseline pipeline with VirusTotal enrichment.
      \item \texttt{baseline\_vt\_pred\_category}: VT-enriched baseline label normalised to the
            evaluation categories.
      \item \texttt{baseline\_vt\_duration\_sec}: Wall-clock runtime (seconds) for the VT-enriched
            baseline pipeline.
      \item \texttt{llmrag\_label}: Raw label produced by the LLM+RAG pipeline.
      \item \texttt{llmrag\_pred\_categories}: Inferred LLM+RAG labels.
      \item \texttt{llmrag\_duration\_sec}: Wall-clock runtime (seconds) for the LLM+RAG pipeline.
      \item \texttt{explanation\_present\_baseline}: Whether the baseline output included an
            explanation/rationale (boolean).
      \item \texttt{explanation\_present\_llmrag}: Whether the LLM+RAG output included an
            explanation/rationale (boolean).
      \item \texttt{grounding\_ge2\_llmrag}: Whether the LLM+RAG output included at least two
            citations to retrieved documents (evidence grounding; boolean).
\end{itemize}

\subsection{Data Ingestion for RAG Corpus}\label{subsec:RAGIngestionExec}
The retrieval corpus was assembled per Chapter~\ref{sec:DataSources} and the ingestion
guide~\cite{rexisIngestionPipeline}. Sources and windows: \textbf{VX-Underground APT write-ups} (1
Jan 2022 --- 1 Aug 2025), \textbf{Malpedia} articles (1 Jan 2022 --- 1 Aug 2025), and
\textbf{MalwareBazaar} metadata filtered to PE-focused tags (e.g., trojan, ransomware, botnet,
rootkit, \texttt{exe}). Only metadata and prose documents were indexed; binaries were excluded.

To automate this process and ensure consistent ingestion, a dedicated ingestion pipeline was
implemented. The details on data source and ingestion are outlined on the next subsections.

\subsubsection{VX-Underground APT Writeups sourcing and ingestion}\label{subsubsec:VXUIngestionExec}
The APT write-ups from VX-Underground were sourced using a browser workflow to collect PDF links
and download locally, as recommended in the guide~\cite{rexisDataSourcingVXU}. Collected PDFs were
then ingested into the \gls{pgvector} store with typed PDF ingestion, following the ingestion
guide~\cite{rexisIngestVXU}.

Ingestion command example (2022 batch):
\begin{verbatim}
pdm run rexis ingest pdf --dir ./data/corpus/vxunderground/2022 \
  --batch 5  --metadata source=vxu --metadata year=2022 \
  --out-dir ./data/ingest/vxu --run-name vxu-2022
\end{verbatim}

The ingest command validates mutually exclusive \texttt{--dir}/\texttt{--file}, splits the workload
into batches (\texttt{--batch}), extracts text with PyMuPDF, normalises and chunks prose (~500
words, with 50-word overlap), embeds with OpenAI, and writes to PgVector. A JSON run report is
written to \texttt{<out-dir>/ingest-analysis-\textless RUN\_NAME\textgreater{}} with parameters,
counts, and timings.

\subsubsection{Malpedia sourcing and ingestion}\label{subsubsec:MalpediaIngestionExec}
The dedicated collector is used to merge the Malpedia references index with the BibTeX dump, apply
AND-filters, and optionally download+ingest referenced documents (PDF/HTML/TXT). The collector
writes a normalised JSON plus a run report; with \texttt{--ingest} enabled it also pipelines the
referenced documents through the ingestion stack~\cite{rexisDataSourcingMalpedia}.

Ingestion command example (collection window + filters; writes JSON):
\begin{verbatim}
pdm run rexis collect malpedia --family-id "^win\\." \
      --start-date 2025-01-01 --end-date 2025-06-30 --max 500 \
      --output-dir ./data/malpedia --run-name malpedia-h1-2025
\end{verbatim}

Ingestion command example (collect + download + ingest referenced docs):
\begin{verbatim}
pdm run rexis collect malpedia --search-term "(fin7|paperbug|qakbot)" \
      --start-date 2024-01-01 --end-date 2025-08-24 \
      --output-dir ./data/malpedia --run-name malpedia-fin7-2024-2025 \
      --ingest
\end{verbatim}

If documents are downloaded separately (e.g., HTML snapshots), they can be ingested explicitly
using the typed HTML or TEXT ingesters:

Ingestion command example (manual HTML):
\begin{verbatim}
pdm run rexis ingest html --dir ./data/corpus/malpedia/html \
      --batch 5 --metadata source=malpedia \
      --out-dir ./data/ingest/malpedia --run-name malpedia-html
\end{verbatim}

The ingestion pipeline performs parsing/cleaning, chunking, embeddings, and indexing; metadata such
as \texttt{source=malpedia} is preserved for retrieval-time filtering.

\subsubsection{MalwareBazaar metadata sourcing and ingestion}\label{subsubsec:MalwareBazaarIngestionExec}
MalwareBazaar entries were collected either by tag(s) (with a per-tag fetch cap) or by explicit
SHA-256 list(s). Results are saved as a normalised JSON array and can be directly ingested into the
datastore with \texttt{--ingest}. An API key is required via config or
environment~\cite{rexisDataSourcingMB}.

Ingestion command example (collection by tags; per-tag cap; writes JSON):
\begin{verbatim}
pdm run rexis collect malwarebazaar \
      --tags trojan,ransomware,botnet,rootkit --fetch-limit 100 \
      --output-dir ./data/malwarebazaar --run-name mb-tags-100
\end{verbatim}

Ingestion command example (collection by hash file; ingest JSON):
\begin{verbatim}
pdm run rexis collect malwarebazaar --hash-file ./data/hashes.txt \
      --output-dir ./data/malwarebazaar --run-name mb-hashes-2025-08-24 \
      --ingest
\end{verbatim}

When collected as JSON (either mode), you may also ingest explicitly using the typed JSON ingester,
attaching provenance metadata for retrieval filters:

Ingestion command example (manual JSON; provenance metadata):
\begin{verbatim}
pdm run rexis ingest json --dir ./data/malwarebazaar \
      --batch 4 --metadata source=malwarebazaar \
      --out-dir ./data/ingest/malwarebazaar --run-name mb-json-ingest
\end{verbatim}

The ingestion pipeline treats each JSON record as a document (ID derived from \texttt{sha256\_hash}
when present), splits large payloads into token-safe chunks, embeds, and writes to PgVector; a run
report is emitted under \texttt{--out-dir}.

\section{Interpretation of Findings}\label{sec:InterpretationOfFindings}
% Analyse and interpret the significance of the results in relation to your research questions.
% Discuss:
%   - How RAG improved static analysis (accuracy, relevance, interpretability)
%   - Where the LLM pipeline underperformed and possible causes
% Cross-reference previous literature (e.g., Fujii 2024, Gao 2023) to contextualise your outcomes.
% Discuss whether findings were expected, and any surprises or anomalies encountered.
For the sake of brevity, and because both the \textbf{Baseline} and the \textbf{Baseline+VT}
pipelines produced identical results across all metrics, they are referred to collectively as
\textbf{Baseline} in this discussion. The experiments evaluated a joined set of 20 samples across
three dimensions (see Section~\ref{sec:EvaluationFramework}): accuracy, efficiency, and
interpretability, with a composite score providing a normalised measure of performance (equal
weights 1/3 for each dimension). Results cited here reference
Tables~\ref{tab:per-sample-results-baseline},~\ref{tab:per-sample-results-llmrag},
and~\ref{tab:results-summary}. Throughout this section, “valid classification” denotes predictions
excluding abstentions.

\subsection{Accuracy and Robustness}
The results show a clear, though not absolute, advantage for the \textbf{LLM+RAG} pipeline. Out of
20 total samples, the \textbf{Baseline} produced 20 classifications, 2 of which were correct
(10.0\%, Wilson 95\% CI: 2.8--30.1). In comparison, the \textbf{LLM+RAG} pipeline produced 18
classifications, 5 of which were correct (27.8\%, Wilson 95\% CI: 12.5--50.9). While absolute
accuracy remained modest in both cases, the relative improvement achieved by \textbf{LLM+RAG}
aligns with prior research indicating the capacity of retrieval-augmented models to contextualise
and generalise better than rule-based approaches~\cite{fujii2024llm, gao2023retrieval}. The
abstentions observed in two of the \textbf{LLM+RAG} classifications are due to a built-in guardrail
where the model was instructed to not pass judgement when insufficient evidence is retrieved. Both
abstentions occurred in the \textbf{botnet} tag (see Table~\ref{tab:per-sample-results-llmrag}).

Per-tag, improvements were concentrated in \textbf{trojan} and \textbf{ransomware}, while
\textbf{rootkit} showed mixed outcomes but consistently grounded rationales. \textbf{Botnet} had
the two abstentions, reflecting stricter guardrails where retrieval was insufficient.

\subsection{Efficiency}
With respect to latency, the \textbf{Baseline} averaged 90.8 seconds per sample, while
\textbf{LLM+RAG} averaged 97.1 seconds. The small increase reflects the added overhead of embedding
generation, retrieval, and model inference. Prior work on \gls{rag}-enhanced architectures reports
similar trade-offs between computational cost and analytic depth~\cite{gao2023retrieval,
      lewis2020retrieval}. In practice, the gap was not prohibitive, suggesting that richer semantic
analysis can be achieved without disproportionate performance loss.

As discussed in Section~\ref{sec:Limitations}, this interpretation is limited to processing time
and does not account for monetary cost from token usage in the \gls{openai} API for \gls{gpt4o}
queries.

\subsection{Interpretability and Transparency}
Interpretability emerged as the most significant point of divergence. Both pipelines achieved
complete explanation coverage, yet the content and quality of those explanations varied. The
\textbf{Baseline} relied on heuristic rules, with only 48.7\% of triggered rules being consistent
with the final assigned category. This indicates that static thresholds and rule sets are brittle
and may fail to adapt effectively to novel malware behaviours. By contrast, every \textbf{LLM+RAG}
classification was grounded in retrieved evidence, with all explanations citing at least two
relevant references. This aligns with arguments in the literature that emphasise the value of
grounding as a defence against speculative or hallucinatory outputs~\cite{sahoo2024systematic,
      wong2021practice}.

Example: for one \textbf{trojan} sample, \textbf{LLM+RAG} cited API-hooking behaviour and a
command-and-control routine from two retrieved reports to justify a trojan/backdoor tag, whereas
the \textbf{Baseline} triggered a generic ``packed'' rule inconsistent with the final category.

\subsection{Composite Outcomes and Implications}
The composite scores, derived from equal weights across accuracy, efficiency, and interpretability,
allow for benchmarking of the two approaches. The \textbf{Baseline} achieved 0.28, whereas
\textbf{LLM+RAG} reached 0.43. This was driven by improvements in accuracy and transparency, which
outweighed the modest loss in efficiency (see Table~\ref{tab:results-summary}). These findings were
expected, given the state-of-the-art capabilities of \glspl{llm} in reasoning over retrieved
evidence~\cite{nourmohammadzadeh2024llmsurvey, ferrag2024allinsights}.

However, the relatively low absolute accuracy across both pipelines was more surprising. This may
be attributed to a few factors discussed on a later section (see Section~\ref{sec:Limitations}).

Nonetheless, the experiments confirm that integrating retrieval and \gls{llm}-driven reasoning into
static analysis provides measurable advantages in classification reliability, interpretability, and
adaptability.

\section{Conclusion}\label{sec:ChapterConclusion}
% Recap the chapter by:
%   - Summarising what was implemented and what results were achieved
%   - Highlighting how your work addresses the research objectives
%   - Providing a closing reflection on the value of combining LLMs and RAG for static malware analysis
%   - Transitioning into the final conclusion chapter
This chapter detailed the design and implementation of a modular system for static malware analysis
and a head-to-head evaluation between a deterministic \textbf{Baseline} and an evidence-grounded
\textbf{LLM+RAG} pipeline. The ingestion stack, retrieval store, orchestration components, and
guardrails were outlined, and a fixed Windows \gls{pe} cohort of 20 samples across four tags was
evaluated.

Empirically, \textbf{LLM+RAG} increased category accuracy from \textbf{10.0\%} (2/20) to
\textbf{27.8\%} (5/18) with \textbf{2} abstentions, with only a modest latency change
(\textbf{90.8\,s} to \textbf{97.1\,s}). Explanation coverage reached \textbf{100\%} for both
pipelines; grounding (\(\geq 2\) citations) reached \textbf{100\%} for \textbf{LLM+RAG}, yielding a
higher composite score (\textbf{0.43} vs \textbf{0.28}). These results support the use of retrieval
to contextualise static features and to produce transparent, auditable decisions.

Limitations include the small, static-only cohort; tag-based ground truth; corpus coverage; and
provider variability. Counting abstentions as errors, \textbf{LLM+RAG} attains \textbf{25.0\%}
(5/20) compared with \textbf{10.0\%} for the \textbf{Baseline}. Operational costs beyond execution
time were not analysed. Despite these constraints, the findings indicate that \gls{llm}+\gls{rag}
is a viable and more interpretable alternative to heuristic-only baselines, and a practical aid for
triage.

The next chapter concludes the thesis by synthesising contributions, reflecting on limitations, and
outlining future work: scaling labelled datasets, hybrid static+dynamic pipelines, improved
retrieval and model/guardrail tuning, and deployment-oriented evaluations.
